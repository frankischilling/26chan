# Staff authentication and moderation slice

The supplied implementation prompt authorizes an independent staff application. This work can proceed while media execution remains blocked on a reviewed processing tier. Public reference material does not specify staff behavior; all staff interfaces are project-defined.

The staff Axum application uses its own origin and validated configuration. WebAuthn user verification is required. Registration/authentication challenges remain on the server, have short expiration and are consumed once. Sessions are opaque random values stored as hashes, with expiration and revocation checked against protected identity data for every protected operation. Host-only cookies are HttpOnly and SameSite=Strict, Secure in production. Development exceptions require loopback. State-changing requests require the exact staff origin, appropriate Fetch Metadata and a session CSRF token. Responses are private and no-store.

Use maintained `webauthn-rs` 0.5.5 passkey flows with required user verification and no password, shared default, recovery-code login or user-presence-only fallback. Hardware-backed credentials are preferred; this slice must accurately state whether attestation is enforced. The library's current official documentation is https://docs.rs/webauthn-rs/0.5.5/webauthn_rs/ and https://github.com/kanidm/webauthn-rs/tree/master/tutorial. Document any native crypto dependencies.

The operator provisions accounts and high-entropy single-use enrollment invitations using a separate CLI and the migration credential. Invitation material is written to an explicitly selected private file, never printed in logs or committed. Enrollment grants a credential for the preselected account/role; it cannot select its own role. Recovery revokes prior sessions and credentials before issuing a replacement enrollment invitation. There are no bootstrap public routes or shared defaults. Online staff cannot grant themselves roles. Role administration and revocation are operator-controlled in this slice.

Use separate `board_auth` and `board_staff` PostgreSQL logins in the staff process. The former can operate only the authentication records needed for ceremonies/sessions/credential counters; runtime grants cannot create accounts, change account roles or enroll without a live invitation. The latter reads content/reports and updates only moderation state plus append-only audit records. It cannot read identity data, create schemas, assume migration authority or read deployment configuration. Public and media credentials cannot access either protected authority. The identity grants in the foundation were reservations, not an implemented authentication boundary; migrations must narrow them as necessary.

Implement login/enrollment/logout, a safe report queue, close/reopen and sticky/unsticky thread actions, post/thread removal and report resolution/dismissal. Deny unknown roles and missing, invalid, expired, revoked or unavailable sessions. Sensitive changes require recent WebAuthn authentication. Moderation operations serialize with public mutations through the board lock, check object/board relationships, and update modification times and audit records in the same transaction as content changes. Use shared typed formatting plus escaped Askama templates in previews. Do not insert user strings into HTML/JavaScript.

Test the actual application and PostgreSQL identities. Use Playwright's virtual authenticator only as a synthetic test fixture, never a runtime bypass. Verify at least one full enrollment/login/moderation/logout browser flow with a real persisted change and authorization failures. Unit and HTTP tests cover negative session/CSRF/origin state and safe previews. Report hardware authenticator validation, production identity provisioning and independent security review as unverified until actually performed.

No production deployment or merge is authorized. This slice has a separate issue and draft PR/checkpoint if practical, preserving the media branch work and coherent commits. New schemas extend the existing versioned migrations; published migrations are never edited.
