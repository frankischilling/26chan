# Public presentation integration

The September 30, 2026 continuation expands the mobile-header integration in
[PR #187](https://github.com/frankischilling/26chan/pull/187). It adds
[post tooltips](post-tooltips.md), preserves the original post-number actions,
and corrects the resize synchronization that stopped its third hosted run.
The earlier header work and inspected screenshots are recorded in
[mobile verification](verification-mobile-post-headers.md).

## Reference and behavior

Core v1128 and extension v1191 supply 19 relative-date vectors, the name-hover
callback and the 300/500 ms delays. The replay checks both release hashes and
the exact bounded helpers before evaluating synthetic inputs. It does not
initialize either released client. The direct subject callback returns no
value for the formatter's shape; subjects keep their escaped native title.
Filename callback vectors remain reference evidence only.

Eighteen style cases use the released core's tooltip placement and six pinned
stylesheets. They cover left, center and right targets in Chromium
151.0.7922.34, with Arial at 1280 by 900 pixels and density 1. The production
controller matches those Windows cases. The right-edge case retains the
released order of operations: height is measured before horizontal placement
can change wrapping. No reference values were changed to fit the implementation.

Names and dates come from the validated original-post recipe. Fixed statistics
labels use a finite vocabulary. Text is inert, global callback names are never
invoked, and tooltip creation adds no network or storage authority. Local-date
title suppression restores only its own value. Cancellation covers pending
timers, exit, resize, scroll, disablement, theme changes, detached posts and
BFCache suspension.

## Failure corrections

The [third hosted run](https://github.com/frankischilling/26chan/actions/runs/36752167694)
passed Windows, privileged media and monitoring qualification, then failed the
Quick Reply resize assertion. Its trace measured the old 980 px right edge
before the browser delivered the requested resize. The test now registers a
one-shot resize witness before changing the viewport and waits for that event
before checking the panel. Geometry, content, storage assertions, timeouts and
zero retries remain intact. The 16 settings-transfer and catalog-lock cases
passed with that synchronization.

A fresh local Rust run reproduced the disposable HTTPS proxy's certificate
being reported as not yet valid. The fixture now issues an explicit validity
window starting five minutes before its generation time and ending one day
later. OpenSSL verifies acceptance inside the window and rejection both before
and after it. The actual proxy still verifies the certificate chain and peer
name; no verification bypass or request retry was added. The focused HTTPS
round trip passed. This narrows the fixture's clock sensitivity without
establishing the cause of the earlier clock discrepancy. The options follow
the [OpenSSL ca reference](https://docs.openssl.org/3.0/man1/openssl-ca/).

Another full run reached the hard connection deadline before its retirement
test could establish earlier closure. That regression now uses controlled
Tokio time with real TCP sockets and an independent three-second wall-clock
bound. The clock advances to 3.6 seconds, after 3.5-second retirement and before
the four-second hard deadline. Silent, partial-first and partial-reused requests
must close without entering the router. Automatic clock advancement is held
during socket I/O, following the [Tokio pause reference](https://docs.rs/tokio/1.50.0/tokio/time/fn.pause.html).
Runtime deadlines and dispatch behavior are unchanged.
