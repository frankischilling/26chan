# Global search compatibility

The public search page follows the pinned source page and client at `/globalsearch.php`. Its hash uses `#/query/board/page`, with `all` standing in for a global search when a page number is present. The browser shows 10 thread results per page and allows at most 10 pages.

The historical client called a separate `find` service whose implementation is not present in the supplied source tree. This rewrite keeps the same browser-facing result shape but serves it from the public application at `/search/api`. The query runs with the public database role and therefore inherits board and post row-level visibility rules.

To keep the reconstructed service bounded, each request searches the newest 20,000 visible posts, groups matches by thread, and returns at most 10 threads for the requested offset. A result contains the thread OP and at most five matching replies. Each returned comment is projected by PostgreSQL to at most 1,024 characters before it reaches the web process; matching comments are excerpted around their first match, while subject-only matches and nonmatching OP context use the beginning of the comment. Links still point to the complete stored post. The full query hash, including `#/`, is limited to 512 UTF-16 code units as in the source. API offsets are limited to 0 through 90 in steps of 10, and JSON output is capped at 1 MiB. Search compares the query case-insensitively against the complete stored subjects and comments. These limits are part of the local service contract because the missing historical backend provides no source-backed index or resource policy to reproduce.

The API carries only Askama-rendered post fragments plus board/thread identifiers. The browser reads the JSON through a byte-bounded streamed decoder, parses every post fragment through the same inert parse5 recipe validator used by native updater/preview responses, and constructs DOM nodes from that validated recipe. Search never inserts response HTML directly into the live DOM.

`npm run test:global-search` checks the generated bundle, nine parser/transport/lifecycle cases, four persisted Chromium scenarios, and two direct-hash scenarios at 1280 and 390 pixels. The browser scenarios cover scoped and global results, escaped hostile text, long-comment excerpts, deleted threads, private-board exclusion, 12-thread pagination, direct page restoration, empty results and malformed requests. They also check the actual search page CSP and browser policy violations. Run it after loading the disposable database environment as described in the README.

Hash parsing uses the source `split("/").slice(1)` grammar and `0 | page` coercion before the page range clamp. A slashless hash clears the query; hexadecimal, fractional, non-finite and wrapping page values follow JavaScript ToInt32. The length check runs before percent decoding. Malformed escapes produce a controlled error and cancel the previous request. The unchanged source methods in `tests/fixtures/global-search-source.json` supply the expected values for the hash table and browser cases. The table also rejects mutations that restore the former prefix-length, slashless-query or decimal-parseInt behavior.
